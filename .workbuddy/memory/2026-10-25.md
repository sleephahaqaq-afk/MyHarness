  且被 WorkBuddy shell 的 safe-delete bulk guard 拦截（pip 卸载旧包删太多文件）。

  下 import 与运行时（create_deep_agent + invoke）均正常，共用环境零升级。
- Bash 工具的坑：`python -c "...\n..."` 里的反斜杠会被转成 `/`，用 `-c` 探测 YAML
  行为会得到假结果；**诊断一律写成 .py 脚本再跑**。
- langchain 1.3 的 `Runtime` 字段：context / store / stream_writer / heartbeat / previous /
  execution_info / server_info / control。**thread_id 在 `runtime.execution_info.thread_id`**，
  不在 configurable；兜底用 `langgraph.config.get_config()["configurable"]["thread_id"]`。

### 追加：记忆抖动真 bug + 前端接线

- **抓到记忆重复写的真因**：`precompute_context()` 每次装配 agent 都调
  `migrate_legacy_preferences()`，而 `user-preferences/<uid>` 是语义记忆的**投影**
  （`merge_preferences` 写完语义会 `_sync_preference_projection` 回写）。迁移不幂等 →
  每次重启都把 0.8 的语义记录用 0.6 重写一遍并顶掉 → 置信度在 0.8/0.6 间抖动 +
  历史版本名额被同内容吃光。修：迁移跳过「语义里已有效的 key」；`write_semantic`
  同值不再产生新版本（只把 confidence 取高者，算强化不算改主意）。
- 三条测试锁住：`test_same_value_does_not_create_new_version_and_keeps_confidence`、
  `test_migrate_legacy_preferences_is_idempotent_across_restarts`、

## 「无法联网检索」故障定位（用户贴回的 agent 回答）

两个叠加的原因，都不是"模型不愿搜"：

1. **`.env` 缺 `WEB_SEARCH_MODEL`**（`.env.example` 有、真实 `.env` 没有）。`web_search`
   在发请求前就返回「未配置…联网搜索已禁用」。补 `WEB_SEARCH_MODEL=gpt-6-luna` +
   `WEB_SEARCH_MAX_TOKENS` + `WEB_FETCH_MAX_CHARS`（顺便消掉代码里的隐式默认值）。
   - 判断抽成 `web.search_config_missing()`，`/api/health` 复用同一份，
     新增 `web_search_ready` / `web_search_missing` 两个字段。
   - 端点实测：`stariver.top/v1/responses` 支持 `{"type":"web_search"}`（3 次 web_search_call、
     正文 1660 字带来源）；`web_search_preview` 被 400 拒。该中转没有 deepseek 系列，
     可用模型是 gpt-6 / gpt-6-luna / gpt-5.6-* 等 11 个。

2. **全基座没有「当前时间」注入**（grep `当前时间|today|datetime.now` 在 prompts/middlewares
   里全为空）。子 Agent 因此认为今天是 **2026-02-06**，把 2026-10-18~25 判成未来，
   直接输出「该时间窗尚未到来，未检索来源」——搜索工具一次没调。
   - 新增 `middlewares/clock.py`：`ClockMiddleware` 每次模型调用现算并替换 `<!-- LIVE_CLOCK -->`
     槽位（无槽位则追加）。**必须每轮现算**，写死在提示词里长跑服务会漂移。
   - 主 Agent 挂在 `HarnessPhase` 之后；子 Agent 通过 `SubAgent.middleware=[ClockMiddleware()]`
     在 `loader.resolve_subagent_tools` 里挂——子 Agent 是独立图，主 Agent 中间件不传递。
   - 测试：`test_clock_middleware_replaces_slot_with_today`、`..._appends_when_no_slot`、
     `test_subagents_carry_clock_middleware`。

验证（真实模型 gpt-6-luna，端口 8010）：修复后同一问题 → 委派 `ai-news-scout`，
`web_search`×11 + `web_fetch`×6，输出 3679 字，按 7 段契约给出带日期与来源的条目，
并主动把 9-22 / 10-07 的条目排除在时间窗之外。全量测试 **73 passed**。

坑：用户自己起过一个 8000 端口的后端（17:20），跑的是旧代码 + 旧环境变量；我没杀它，
改用 8010 验证。改 `.env` 或中间件后**必须重启服务**才生效。

## web_fetch 两类抓取失败的定位（用户报 OpenAI 403 / arXiv 读取失败）

1. **OpenAI 新闻页 403**：Cloudflare 在 TLS 指纹层拦 httpx，换 Chrome UA 也 403，无解。
   正解是它家 RSS：`https://openai.com/news/rss.xml` → 200、1318 条、带 pubDate+link，
   httpx 直抓可用。sources.md 已把 OpenAI 入口换成 RSS 并标注"HTML 页别用"。
2. **arXiv "未能读取"两个叠加原因**：
   a. E2E 里模型传了 `max_chars=120`，被 floor 截成 500 字符残片，读不出任何 entry →
      sources.md 新增 max_chars 指引（feed/API 给 12000–16000，宁大勿小）；
   b. **沙箱代理对 export.arxiv.org 间歇/持续 502**：WorkBuddy Bash 沙箱注入
      HTTP(S)_PROXY，该代理层 502 arXiv；无沙箱直连 9/9 全 200。用户自己终端起的
      服务不受影响。缓解：web_fetch 对 TransportError 自动重试一次（新增两条测试），
      sources.md 加兜底 `https://arxiv.org/list/cs.AI/recent`（沙箱内实测 200）。
   - 教训：同一 URL 在"沙箱内跑的测试服务"与"用户终端跑的服务"网络路径不同，
     排障前先确认执行环境的代理变量（`env | grep -i proxy`）。
- 测试 75 passed。
